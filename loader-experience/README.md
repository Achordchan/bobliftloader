# BOB-LIFT 产品叙事样片 · V2

## 本轮方向

由“首屏固定展台、整页切换镜头”改为真正的长页面：

1. 深色整机开场：标题上移退出，整机放大进入细节叙事。
2. 整体过渡：文字逐段出现，配合短距离环绕。
3. 履带底盘：独立滚动章节，放大轮组和履带，显示部件标注。
4. 液压前端：深色高清特写推进，举升臂、油缸和连接接口依次介绍。
5. 站驾操纵：操纵台靠近，三项结构说明分步出场。
6. 站立踏板：独立近景和防滑凸纹说明。
7. 整机收尾：360/460共用外观说明，实拍对照及返回开场。

所有介绍使用已知的结构事实，没有加入未确认的载荷、功率、速度等性能参数。原厂模型与照片不一致的部件仍有精度限制。

## 卡顿相关改动

旧实现滚动到目标帧才开始解码，缓存淘汰后又可能需要重新解码；缺帧时显示其他已缓存帧，会形成跳帧感。120帧还承担了较长的环绕与变焦。

V2不再让整页滚动驱动120张大图。主体章节使用独立高清渲染图，通过transform做连续缩放和平移。短环绕仅使用24张680px图，进入章节前准备并解码完毕，再启用动画；手机解码到480px。滚动期间只绘制已经准备好的图，不触发解码、不淘汰后重建，也不叠画相邻两帧。

这属于实现层面的性能调整，实际流畅程度尚未验证。


## 本轮验证状态

用户要求先自行验证，因此本轮没有运行语法检查、测试命令、浏览器、截图或性能验收。只执行了文件修改、必要的素材渲染和编码，没有把V1的通过记录作为V2验收结论。

布局影响已在代码层面考虑：每章独立滚动范围，移动端重排，减少动态效果时使用静态章节。尚未观察实际桌面/手机画面，可能仍需调整裁切、文字位置、动画节奏与设备性能。

本轮没有修改原网站或Blender工程，没有新增生产依赖。旧展台逻辑已从当前入口移除；原素材和代码归档保留。

## V4：实时三维、爆炸拆解与部件实拍对照（2026-09-22）

当前版本以本节为准。V3 的预渲染视频章节（履带、举升翻斗、操纵台、踏板）保留，前面新增了真正使用三维模型的章节。

### 页面结构

1. **首屏实时三维**：`loader-cad-restored.blend` 导出的 GLB 在浏览器中实时渲染（three.js r186，本地 `assets/vendor/three/`），自动缓慢旋转，可拖动任意角度查看（不响应滚轮，滚轮始终用于翻页）；静态图作为加载前占位及无 WebGL 的回退。
2. **实拍环绕**：11 张绕机拍摄的实拍（IMG_2724 → 2719）组成可拖动、可随滚动转动的照片转台，与三维模型互相印证。
3. **结构拆解（爆炸图）**：13 个装配组（车架、大臂、铲斗、快换架、履带架、左右履带轮组、液压油缸与管路、操纵台、发动机与散热、汽油箱、液压油箱、电瓶）随滚动沿装配方向分离，也可用滑杆和“全部拆开 / 复位整机”按钮控制。每组带有跟随三维位置的标签，点击标签或模型本体打开该部件的实拍照片。
4. **逐个部件**：左侧 8 个部件卡片，滚动到某张时右侧固定的模型自动飞到该部件并把其余结构淡为半透明；卡片缩略图打开该部件的实拍集。
5. **实拍弹窗**：统一的灯箱，含左右切换、缩略条和键盘方向键；收尾“查看实物照片”改为打开 15 张整机实拍。

### 素材与脚本

- `assets/model/loader.glb`：2.8 MB，meshopt 压缩，13 个节点按装配组命名，约 27.6 万三角面。由 `scripts/build_model.sh` 生成：Blender 在导出时把每个集合合并为一个对象（不修改工程文件），再用 gltf-transform 压缩。`scripts/export_glb.py` 中的 `group_of` 表决定集合到装配组的映射。
- `assets/site/`：65 张现场实拍的 1800px WebP 及 `thumb/` 420px 缩略图，来自 `照片/红色 360-460 站 /IMG_*.jpg`，未做裁切或修饰。
- `viewer.js`：three.js 查看器封装（加载一次、多实例克隆、爆炸偏移、聚焦飞行、半透明淡出、标签投影、可见时才渲染）。`explore.js`：部件数据、照片分组、爆炸与部件章节绑定、灯箱。`turntable.js`：照片转台，取代 V2 的 24 帧渲染环绕（`sequence.js` 与 `assets/orbit/` 保留未删除，但不再被页面加载）。`viewer.css`：以上章节样式。
- 爆炸方向、部件说明文字和照片归类均为展示用途，基于可见结构编写，没有加入载荷、功率等未确认参数。

### 验证

Chrome 内置浏览器实测桌面 1440×900 与手机 375×812：模型加载、自动旋转、拖动、滚动爆炸、标签点击打开实拍、部件聚焦淡出、无横向溢出、控制台无错误（仅 three.js 关于 `THREE.Clock` 的弃用警告）。未在 Safari / Firefox、真实手机及低端 GPU 上验证性能；三个 WebGL 上下文同时存在，旧设备上可能需要合并为单一渲染器。

## V5：真实感、实时机械动作与照片归类修正（2026-09-22）

当前版本以本节为准。

### 真实感

- **HDRI 环境光**：`assets/env/sky.hdr`（Poly Haven CC0 “kloofendal_48d_partly_cloudy”，缩至 768×384）经 PMREM 作为环境贴图和反射来源，替换 three.js 内置的合成房间环境。
- **烘焙 AO**：`scripts/export_glb.py` 在导出前为每个装配组做 smart UV 展开并用 Cycles 烘焙环境光遮蔽（大件 2048、小件 1024），保存为 `assets/model/ao/<组>.webp`，网页按组挂到材质的 aoMap。烘焙前重算法线，否则 STEP 三角化的部分壳体朝内会把 AO 烤成黑色。
- **材质**：全部改为 MeshPhysicalMaterial。喷漆带清漆层，橡胶带 sheen，所有非镀铬材质叠加程序化噪声粗糙度贴图，去掉 CAD 的“完美塑料”感。色调映射用 Neutral，车身红取实拍采样值。
- **光照**：暖色主光对齐 HDRI 亮区，软阴影 1536 贴图，半球光补暗部。

### 实时机械动作（替代 V3 的两段预渲染视频）

- 导出时把液压集合拆为 `liftBarrel / liftRod / tiltBarrel / tiltRod`，软硬管路和快接头归入臂架组、大臂固定销归入车架、铲斗连接销归入铲斗。铰点由 `export_glb.py` 按 `mechanical_rig.py` 的参考位置从 CAD 零件中选取，写入 `assets/model/loader.json`。
- `viewer.js` 的 `buildRig` 建立 车架 → 臂架铰点 → 铲斗铰点 的层级，四个油缸半体各挂在自己的销轴组上；`setPose(lift, tilt)` 让缸筒与活塞杆始终对准对方销轴，镀铬杆身沿轴向随行程伸缩（销耳不变形）。数值校验：五种姿态下缸筒与杆的轴向与销轴连线夹角余弦均为 1.0000。
- 新章节“03 / 机械动作”滚动驱动 举升 → 翻斗 → 回落，可用滑杆或播放按钮控制，可拖动换视角，右上角保留三段实机视频对照。
- 举升 70°、翻斗 −48°/+18° 为展示用行程，未经厂家标定；铲斗在举升时按 90% 反向补偿保持大致水平，是简化的自调平近似。

### 页面结构调整

- 原“站驾操纵”“站立空间”两章删除，文案并入“逐个部件”的操纵台和车架卡片；原“行走系统”“作业前端”视频章节由机械动作章节替代。`motion.js`、`motion.css`、`chapters.css`、`sequence.js` 及 `assets/motion/`、`assets/orbit/` 保留未删除，但不再被页面加载。
- 部件照片归类按人工复核修正 9 张：液压快接头与油位观察窗、踏板与铲斗、整机正面与发动机舱等原先互相放错。

### 验证与限制

内置 Chrome 桌面 1440×900 与手机 375×812：模型、AO、HDRI 载入无报错；举升翻斗随滚动与滑杆变化；铰点校验如上。未验证 Safari/Firefox、真机与低端 GPU。AO 贴图使 GLB 增加 UV 数据（4.4 MB）加 2.5 MB 贴图，首屏载入比 V4 多约 4 MB。

### 环绕实拍章节重做（2026-09-22 晚）

“把复杂的作业，收进紧凑的身形”一节原先直接切换 11 张构图各异的照片，顺序也把左右两侧交错排列，观感生硬。现改为：

- 帧序按实际绕机方向重排（正前 → 右前 → 右侧 → 右后 → 正后 → 左后 → 左侧 → 左前 → 回到正前）。
- `assets/turn/`：11 张照片按车身红色区域自动定位，裁成 3:2、机身居中且大小一致的 1600×1067 WebP。
- `turntable.js` 重写：浮点位置缓动，相邻两帧在 canvas 上交叉淡入；拖动带惯性并吸附到最近一帧；闲置约 4 秒后每 2.8 秒自动转一帧；左右方向键与两侧箭头按钮可用；滚动不再驱动转台，只由拖动、箭头、方向键和闲置自动旋转控制。
- 文案区新增朝向表盘（随视角旋转的俯视小车与标记）、当前朝向名称和帧计数；卡片加投影、底部渐变、拖动提示与分页点。

照片本身在不同位置、不同背景下拍摄，交叉淡入过程中背景仍会短暂重影；若要完全消除，需要在统一转台上重拍或做抠图。

### 模型缺件修正（2026-09-22 晚）

网页模型与 Blender 渲染相比缺少环形扶手、软硬管路、风罩格栅、钥匙和仪表指针。原因是导出脚本只收集 `MESH` 类型对象，而这 42 个照片补充件是带倒角的 `CURVE` 对象。现在导出时把曲线一并转成网格再合并：扶手归操纵台组，管路归臂架组，举升缸供油管归举升缸筒组，格栅归发动机组。

### 应用场景章节（2026-09-22 晚）

新增独立章节“04 / 应用场景”，位于机械动作与收尾之间，没有并入机械动作章节：机械动作讲“怎么动”，场景讲“去哪里用”，合在一起会让单章信息过载，页面深浅节奏（暗 → 亮 → 暗 → 亮）也需要一段浅色章节。

- 三类场景按行业通用用途整理：园林与庭院、工地与改造、农场与牧场。厂家官网没有给出自己的场景说明，页面注明“非具体客户案例”。
- 一个固定舞台，滚动或点击底部标签切换场景：文案卡片淡入淡出，背景色调（草绿 / 土黄 / 稻草黄）随场景过渡，右侧同一台三维模型飞到该场景的机位并缓动到对应姿态（园林：贴地整平；工地：高举倾倒；农牧：铲斗收起搬运）。`viewer.js` 新增 `animatePose`。
- 工地场景附一张真实土方作业照片（主图 0.jpg，仅 800 px，作为小卡片并可放大）。

参考资料：Toro 紧凑多功能装载机产品页、Compact Equipment 的 mini skid steer 综述以及多家厂商的用途描述均把园林、施工、农牧列为主要用途。

场景章节补充：每个场景在镜头到位约 1.5 秒后进入循环作业动效（园林：贴地前后推平；工地：举升 → 倾倒 → 收斗 → 回落；农牧：收斗慢速往返搬运），离开章节即停止。`assets/scenes/garden.webp`、`site.webp`、`farm.webp` 三张空场景底图放入后会自动淡入到模型后方（左侧与上下带渐变遮罩保证文字可读）；文件缺失时控制台会有三条 404，仅是探测，不影响功能。

- 三个场景改为“铲斗贴地 → 前进插入料堆（料随行程长出并逐渐收斗）→ 举升/行驶 → 倾倒 → 倒车回位”，物料不再凭空出现。

## 履带脱落与卸料穿模修复（2026-09-22）

- 履带根因：旧版将每个顶点独立投影到循环路径，同一履带块在转角处被不同幅度拉动。实测三角边最大伸长约14.41倍；左右局部坐标实际上相同，并非左右装配位置不同。
- `track-motion.js`：按位置连接关系识别连续带体、92个履带块和46个导齿。连续带体不变形，138个独立部件沿带体轮廓做刚体运动；保持原UV、材质、索引和接触轮廓。量化GLB只读，应用场景使用独立浮点缓冲区。
- `viewer.js`：接入履带更新，停止/切换时同步复位行走位移与履带；释放自有几何缓冲。其他四个三维视图的共享原始几何经过对照，未变化。
- 卸料根因：旧版把整块料堆直接向下平移0.32米、向前平移0.55米，再降低透明度并隐藏，容易穿过斗底且缺少下落过程。
- `payload.js`：在铲斗局部坐标中对真实CAD网格采样，避开斗壁和后部支架，建立贴合底面的料层。减少的是料层高度，不再将整块料堆穿过斗底。排出的料块在世界坐标中运动，经重力下落和地面接触约束落地，不跟随机身移动。
- `material-flow.js`：装料/卸料速率限制；只有实际斗口朝下才释放物料。不会仅因脚本目标量改成0，就清空尚未翻转的料斗。落地料块保留4秒，再用2秒逐步清理，适用于循环展示；切换场景时统一复位。
- `explore.js`、`index.html`：更新模块版本，移除与实际行走逻辑相矛盾的旧注释。没有改变章节布局或场景介绍。

## 首屏退场：俯视行驶（2026-09-23）

首屏滚动时原本只放大整机，现改为连续镜头，全程由首屏滚动范围驱动（首屏高度由 170svh 增至 280svh，手机 150svh → 240svh）：

1. **转到顶部**（0–45%）：相机脱离自动环绕，从当前角度按最短方向绕到机器正前方并升到近俯视（距竖直约 11°），标题与说明同时淡出。铲斗朝下，“向前”就是“向下”。
2. **收斗**（30–50%）：铲斗收起到运输高度。
3. **行驶出画**（50–100%）：整机由静止加速向前（屏幕向下）驶出，履带使用 `track-motion.js` 的刚体履带块按同一行程滚动，阴影随机身移动。出画距离按俯视相机实时投影包围盒计算，任何屏幕比例都能完全驶出后再进入第二章。

往回滚动时整段倒放；回到顶部时相机、姿态、履带全部复位，自动环绕与拖动恢复。减少动态效果模式不启用此段。

实现要点：
- `viewer.js`：`frame` 选项用 `setViewOffset` 按 `.exp-hero-frame`（原画布位置）构图，画布本身铺满首屏，所以首屏静止画面与之前一致，而机器可以一直开到屏幕底边而不被原画布边界裁掉。新增 `holdCamera()`（暂时接管 OrbitControls）与 `setDrive()`（机身、履带、太阳阴影同步前进）。
- `explore.js`：`bindHeroDrive()` 负责上述编排；首屏查看器开启 `trackMotion`。
- `app.js`：海报图放大仅作为无 WebGL 的回退，不再缩放三维画布。

已在内置浏览器验证桌面与 375×812 手机：俯视居中、履带转动、完全驶出、倒放复位，控制台无报错；`track-motion`、`material-flow` 测试通过。未在真机和 Safari 上验证滚动流畅度。

## 首轮性能优化（2026-09-23）

### 应用场景改为预渲染视频

这一节只做展示、不需要交互，原来却一直在实时运行一整套 3D：独立的 WebGL 渲染器、实时阴影、每帧约 3 ms 的履带 CPU 计算、物料粒子模拟，以及用底图生成的环境光。现在改为每个场景一段循环视频。

- 录制：`scripts/capture_scenes.mjs` 用 Playwright 驱动本机 Chrome（GPU/Metal）打开 `?capture-scenes`。这个模式下保留原来的实时场景，并改用虚拟时钟逐帧推进（`viewer.clock` / `viewer.step()`），机器再慢也不会掉帧。每个循环都录第二遍，第一遍倒出的物料在开头仍在落定，首尾可以无缝衔接。帧率 30fps，时长分别为园林 16.8 s、工地 18.4 s、农牧 20.6 s。
- 编码：H.264 High，BT.709，关键帧间隔 2 秒，开启 faststart 以便边下边播。桌面版 1920×1104、CRF 28，手机竖版 780×1564、CRF 29。首帧另存为 WebP 封面图。输出位置 `assets/scenes/video/<场景>-<desktop|mobile>.{mp4,webp}`。
- 播放（`explore.js` 的 `bindSceneVideos`）：临近本节才开始加载，离开视口就暂停。切换场景时两段视频交叉淡入，新场景从开头播放，同时预加载下一个场景。手机使用竖版视频。开启“减少动态效果”时只显示封面图。这一节不再依赖 WebGL，页面上的 3D 渲染器由 5 个减为 4 个。
- 修改场景动作、光照或底图后需要重新录制，命令如下（需先启动本地服务）：

```sh
PLAYWRIGHT_CORE=<playwright-core 目录> node loader-experience/scripts/capture_scenes.mjs
```

可以用 `--only desktop|mobile`、`--scene garden|site|farm` 只录一部分，用 `--encode-only` 只重新编码已有的帧。

### 其他改动

- 阴影贴图只在场景变化时重新计算（`viewer.js` 的 `step()`）。自动旋转、拖动视角这类只有相机在动的帧沿用上一张阴影贴图，每帧绘制的几何量约减半，对首屏持续自动旋转的效果最明显。
- 实拍轮播只加载当前一张和相邻两张，不再在首次访问时一次下载全部 11 张（约 2.3 MB）。
- 手机端场景构图同时修正：原来竖屏里机器偏右、铲斗出画，左侧还叠着桌面版左栏用的白色渐变。现在手机机位抬高到 1.25 m、机器水平位置 30%，整机入画；手机上去掉左侧渐变，改为上下渐变，底部加深以托住场景卡片文字。
- 视频在页面进入后台时暂停、回到前台续播；开启“减少动态效果”时只显示封面图，不下载视频。

验证：用 Playwright 驱动无头 Chrome，在桌面 1440×900、手机 390×844 和“减少动态效果”三种条件下检查。首屏加载不请求任何场景视频或底图；实拍轮播首屏最多 3 张。滚到三个场景时，当前视频在播放、时间在走，卡片同步切换，桌面和手机各自加载对应版本。循环首尾两帧的差异与正常相邻帧同一量级（无缝）。首屏自动旋转每帧绘制的三角形由 82.7 万降为 41.4 万。未在真机和 Safari 上验证视频播放与发热。

### 3D 渲染器按需创建与释放（2026-09-23）

每个 WebGL 上下文都在 GPU 上单独存一份模型（约 27.6 万三角面）、AO 贴图、环境贴图和阴影贴图。原来 4 个 3D 章节在页面打开时同时创建，始终占着 4 份。

- `viewer.js`：渲染器与场景分离。`wake()` 创建上下文，重新上传几何与贴图，为这个上下文单独预过滤环境贴图，先用 `compileAsync` 在后台编译着色器（浏览器支持时），编译完成后才开始绘制。`sleep()` 释放本视图的材质，调用 `forceContextLoss()` 交还整个上下文的显存，移除画布。场景图和状态（姿态、拆解程度、聚焦部件、相机位置、首屏行驶进度）都保留在 CPU 侧，唤醒后画面不变。相机的宽高比与视口偏移在休眠期间照常更新。
- `explore.js` 的 `manageContexts()`：章节进入视口前后一屏以内时唤醒，离开超过两屏半时休眠，两个阈值之间留出间隔，避免在边界来回滚动时反复重建。首屏的海报图等到首屏模型真正画出第一帧后才淡出。
- 实测（Playwright，桌面 1440×900 与手机 390×844，从顶部滚到底部再滚回）：同时存在的上下文大多为 1–2 个，只在章节交界处短暂为 3 个；原来始终是 4 个（场景章节改为视频之前是 5 个）。每个章节进入画面时都已完成绘制，滚回顶部后首屏唤醒，画面与初次打开一致。

顺带修复的问题：

- **环境光失效**：原来 4 个查看器共用首屏渲染器生成的环境贴图，但这类贴图只存在于生成它的上下文里，结构拆解、逐个部件、机械动作三章实际采样到的是空贴图，一直只有太阳光和半球光照明（实测带不带环境光，亮度都是 33）。现在每个上下文生成自己的环境贴图，这三章有了 HDR 反射，平均亮度约 60–84，与首屏一致。
- 按 three.js r186 的写法把 `RGBELoader` 换成 `HDRLoader`，把 `PCFSoftShadowMap` 换成 `PCFShadowMap`（r186 已经在自动回退到这个类型），效果不变，控制台不再重复出现弃用警告。

已知限制：几何体和 AO 贴图由多个视图共享，所以释放时不能直接销毁它们。three.js 会在这些共享对象上保留指向旧渲染器的事件监听，每经历一次休眠—唤醒，就有一个旧渲染器的 JS 对象（不含显存）无法被回收。唤醒和休眠阈值之间的间隔让这种情况只在大范围来回滚动时才会发生。

### 结构拆解：点击部件后拆解卡住（2026-09-23 修复）

原因：结构拆解一章在画面上第一次按下鼠标后，就永久停止“滚动控制拆解程度”，直到离开本章再回来才恢复。本意是让拖动旋转的用户接管，但点击部件看实拍同样会触发，于是拆解程度卡在点击时的那一帧。

现在：拖动旋转和点击部件只改变视角或打开照片，不影响滚动控制。拖动滑杆、点击“全部拆开”或“复位整机”后，画面保持手动设定的值，直到用户继续滚动约十分之一屏，然后平滑回到滚动对应的拆解程度。打开实拍照片时会清除部件的悬停高亮。已用 Playwright 验证点击、拖动、按钮三种操作之后，拆解程度都会继续跟随滚动。

## 第二轮性能优化：流畅度（2026-09-23）

原则：视觉与原版一致，只去掉浪费。所有数据都用 Playwright 驱动本机 Chrome（GPU/Metal）测得，CPU 限速 4 倍以模拟中端手机，从页首匀速（每秒 0.9 屏）滚到页尾，按章节统计帧间隔。这台 Mac 的 GPU 很强，无法模拟弱 GPU。

### 改动

1. **AO 贴图改为后台解码**（`viewer.js` 的 `loadModel`）。进入结构拆解、逐个部件、机械动作三章时各有约 1.3 秒的整页卡顿，其中约 1.2 秒来自 AO 贴图：`<img>` 在每个 WebGL 上下文首次上传时都要在主线程同步解码。现在用 `ImageBitmapLoader` 在加载时就在后台线程解码一次，各视图共享。浏览器没有 `createImageBitmap` 时回退为 `<img>`。
2. **唤醒时逐帧上传贴图**：`wake()` 在首次绘制前每帧只上传一张贴图，避免集中在同一帧。
3. **AO 贴图分辨率减半**（2.7 MB → 1.0 MB）。与原图在同一机位对比（首屏整机和四个部件特写），PSNR 为 54–61 dB，最大单像素差 22/255，平均差 0.09/255，肉眼无差别。原图归档在 `design/ao-full-res/`。`scripts/build_model.sh` 仍按原尺寸烘焙，输出时减半。贴图地址加上 `?v=2`，避免老访客沿用缓存中的旧贴图。
4. **每个视图只运行一条动画循环**。`tick()` 会在进入视口、加载完成、唤醒完成时各被调用一次，原来没有检查是否已在运行，于是同时跑着多条循环，每帧重复执行 `controls.update()` 和 `step()`。原版首屏一直有 2 条循环，所以大家看到的自动旋转速度和阻尼实际是配置值的两倍。现在只保留一条循环，同时把首屏参数显式设为原版的观感（`autoRotateSpeed` 1.1，`dampingFactor` 0.135，即 1 − 0.93²），视觉与手感不变。
5. **履带不再每帧重算包围体**：两条履带每次更新都要重算包围盒和包围球，4 倍限速下约 4.8 ms。履带块只沿自身环路运动，包围体在建模时算一次，并加 5 cm 余量。更新耗时降到约 1.1 ms。
6. **应用场景改用单个 `<video>`**。实测只要页面里曾有两段视频同时播放（原来的交叉淡入），Chrome 就会把整页刷新降到 30 fps，并保持到刷新页面为止；用三个普通 `<video>` 的最小页面也能复现，暂停、隐藏、卸载都无法恢复。现在切换场景时，先在正在播放的片段上淡入下一场景的首帧静图，淡入完成后在静图下面换片，新片画出第一帧后立即撤掉静图（静图就是首帧，所以没有接缝；每段循环开头本来就有 1.4–1.8 s 的静止停顿）。下一场景的视频用 `<link rel=prefetch>` 预取。
7. **自适应分辨率，只在 GPU 跟不上时生效**（`viewer.js` 的 `adaptQuality()`）。连续 45 帧的帧间隔中位数超过 22 ms，且本视图每帧 CPU 耗时中位数低于 8 ms（说明瓶颈在 GPU 或合成器），就把像素比降低 0.25，最低到 1。降低后的上限在休眠和唤醒之间保留。用伪造帧时间验证过：正常 60 fps 和 CPU 瓶颈时都不触发，GPU 瓶颈时依次降为 1.25、1。在本机的完整滚动测试中，4 个视图都保持原始分辨率。
8. **网站图标**：`favicon.svg`（深色圆角底、白色斜体 B、品牌红圆点，与页头标识一致），另有 `favicon-32.png`、`favicon.ico`、`apple-touch-icon.png`。原先每次访问都有一条 `/favicon.ico` 404。

### 应用场景：尺寸切换重叠、未到先播（2026-09-23 修复）

- **重叠**：跨过 700 px 手机/桌面分界时，视频会切到新版本，但静图只在切换场景时才更新。如果尺寸切换恰好和场景淡入同时发生（布局改变会让滚动触发器重新判断当前场景），就会出现“手机竖版视频被拉到桌面宽度 + 半透明的桌面静图”叠在一起。现在切换尺寸时会取消进行中的淡入，静图和视频一起换到新版本；每次显示都保证两者同属一个版本；视频开始播放 1.5 s 后静图仍未撤掉的话，强制撤掉。
- **未到先播**：原来章节距视口六成屏以内就开始播放，用户看到时动作已经播到一半。现在加载与播放分开：进入六成屏范围只加载并停在第一帧（与封面图相同）；舞台至少 20% 进入视口才从第一帧开始播放；离开视口暂停，下次进入重新从头播放；远离章节时释放视频。
- 验证（Playwright）：进入前已加载、暂停在 0 s，进入 0.7 s 时播放到 0.69 s；在淡入进行到一半时切到手机、再切回桌面，最终视频和静图同一版本，静图不透明度为 0；三种模式（桌面、手机、减少动态效果）播放正常；整页仍保持 60 fps。

### 应用场景：切换时的断层与重影（2026-09-23 修复）

- **断层**：原来用“首帧静图淡入盖住正在播放的视频”做过渡。点底部标签跨场景跳转时，静图还处在上一次淡入的中途（可见状态）就被换了图片地址，新图还没下载完，浏览器先画出已下载的上半截，于是出现一条横向硬边。
- **重影**：两个场景里机器的位置和大小不同，交叉淡入时两台机器叠在一起，像两次曝光。原来的 3D 版本是同一台机器、镜头移动过去，所以没有这个问题。
- **现在**：切换时画面在 0.42 s 内淡到页面底色 `#f5f5f7`（和左侧文字区同色），完全遮住时换片，新片画出第一帧（最多等 0.8 s）后在 0.6 s 内淡出，全程约 1 s，任何时刻只有一个场景在画面上。静图层已移除；进入本章前会预加载三个场景的封面图。
- 验证：逐帧截取“园林直接点到农牧”的过程，遮罩依次为 0 → 0.64 → 1.00（此时换片）→ 0.46 → 0，没有重影和断层。三种模式、尺寸切换、离开再回来都正常，整页保持 60 fps。

### 收尾：机器从上方开进来（2026-09-23 新增）

- 和首屏首尾呼应：首屏里机器往下开出画面，收尾时它从上方开回来。收尾舞台在页首栏下方钉住，钉住期间（桌面约 1.1 屏、手机约 1 屏滚动）跟随滚动：

  2. 铲斗放下（0.5 → 0.7）；
  3. 镜头从顶视落回展示角度（0.58 → 0.94）；到 1 时交还给轨道控制：开始自转，可以拖动，出现“拖动旋转”提示。
- 往回滚：从自转停下的角度接回去，不跳帧；滚回到顶视阶段后，下次再开进来会落回标准展示角度。
- 实现：`bindFinaleDrive()`（explore.js）。3D 画布铺满整个舞台（两侧到页面边缘），展示构图仍以 `.exp-finale-frame` 为准；顶视时视线点下移，让停住的机器压在大字上、不碰到色块。起点用相机副本二分求出“整台机器刚好在画布上沿之外”的距离。参数：`FINALE_REST`（展示距离，桌面 1.1 倍、手机 1.95 倍，因为手机的构图框是竖长的）、`FINALE_TOP`、`FINALE_CUE`。
- 减少动态效果或没有 WebGL：舞台不钉住，直接显示展示状态或静图。封面静图只在机器停好之后才可能出现，行驶途中不显示。
- 收尾整机原来的“缩放入场”动画已删除；大字的字距动画提前到进入舞台前结束。

### 收尾：和首屏同尺寸、同速度（2026-09-23 修正）

- 原来尾部机器比首屏小约三分之一（桌面顶视 413 px 对 615 px）。原因是两边的构图框高度不同，而相机距离是各自手调的。现在按两台相机各自的投影换算，让“每米多少像素”与首屏相同：顶视高度首屏 615 px、尾部 627 px（手机 358 / 354 px）；展示状态也用首屏的机位和尺寸。手机的构图框窄，首屏在手机上本来就略超出屏幕宽度，这里只在装不下时拉远到刚好容纳整机。
- 速度：驶入时屏幕上的最高速度等于首屏拖动字标时的最高速度（`hero.drivePace()`，像素/屏）：桌面 2175 对约 2060，手机 1275 对约 1267。钉住距离由此自动算出（桌面约 1.0 屏，手机约 1.3 屏），`FINALE_CUE` 只保留停车位置、放铲斗与镜头回落的时长（与首屏同为 0.15 屏和 0.37 屏）。
- 按屏幕速度而不是世界速度对齐，是因为镜头从正前方略斜向下看：画面上方离镜头更远，同样一米在屏幕上更短，而机器正是从上方进场。
- 手机上大字在字距动画开始时会折成两行，构图框随之变矮，尺寸换算就会跑偏；已禁止换行，且构图框尺寸变化时重新计算。
- 桌面按首屏尺寸后，展示状态的机器更高：构图框上沿提到产品区上方 40%、下沿收 8%，停好后压在大字上，不碰色块。

### 收尾：提前进场、停稳即可拖动（2026-09-23 修正）

- **提前进场**：原来要等舞台钉住后机器才出发，舞台滚进来的那一屏是空的。现在舞台顶边到达页首栏下方半屏处（`FINALE_CUE.early` = 0.5 屏）就出发。这段时间 3D 画布用 `viewer.setViewShift()` 往上平移，贴住页首栏，机器从屏幕上方开进来，经过参数表末尾，钉住时正好接上；平移不改变画面构图（`resize()` 会扣除平移量）。整段仍按首屏速度，钉住后桌面约 0.2 屏、手机约 0.4 屏停稳。收尾舞台 `z-index: 3`：sticky 会自成层叠上下文，需要整体压过参数表的吸顶表头。
- **停稳即可拖动**：机器停稳、铲斗放下之后（`cues.lower` 结束），按下画布就接管镜头：从滚动脚本当前的位置交给轨道控制，不必滚到底。往回滚进行驶段时，镜头用 0.6 s 从你拖到的角度平滑接回脚本。行驶途中画布不接收指针（`.is-driving`），既不会误拖，也不会挡住上方参数表的点击。

### 多语言与页首标志（2026-09-23 新增）

## 开场加载（2026-09-23）

- 首次打开时，首屏机器先以线稿出现（`assets/details/hero-line.webp`，由 hero.webp 边缘检测生成），随真实下载进度从左到右上色，并有一条红色光边跟随进度。完成后静态图先淡出（略带虚化），三维模型随后淡入；两者不同时出现，因为角度并不完全重合，叠在一起会像重影。
- 模型和环境贴图的下载由 index.html 头部的内联脚本在页面脚本之前发起（`window.__packed`），所以进度从第一秒开始走；viewer.js 直接接手这两个下载。进度按字节计算：模型 + 环境贴图 + AO 贴图，下载阶段最多到 92%，余下是首次绘制。
- 加载期间页面停在顶部（滚轮、触摸滑动、方向键都被拦住），最长 10 秒；点页内链接或播放导览会立即放行。带 `#锚点` 打开或开启了「减弱动态效果」时不锁定。所有脚本执行完仍未启动三维时，恢复彩色静态图。
- 是否播放上色按实际加载时间决定（2026-09-28）：打开后的前 0.4 秒首屏机器位置先留空（`html.hero-pending`），三维在这之内画出来（缓存命中、机器快）就直接淡入，不播上色；超过 0.4 秒才切换为线稿上色和进度条，从当前下载进度开始。原先用 localStorage `boblift-3d` 记住“加载过”，回访一律不播，但缓存只保留一天，而且即使命中缓存，解压、解析和首次绘制也要一两秒，结果回访时页面被锁住却没有任何进度提示。地址加 `?intro` 仍可从第一刻强制播放上色，方便演示。

## 首屏行驶卡顿修复（2026-09-24）

用户反馈首屏“往下开”时很卡。滚动匀速扫过首屏（每秒 0.9 屏），逐帧记录，发现三处固定位置的长帧，都是一次性工作落在行驶中途，不是持续掉帧：

1. **字标出场约 0.45 屏，35 ms**：字标与链条是模型载入后才异步加进场景的，`wake()` 的着色器预编译没覆盖到，第一次出现时现场编译。现在 `LogoTow` 建好后调用 `viewer.precompile()`（新方法，等 `ready` 后对整个场景 `compileAsync`）。
2. **字标淡入约 0.55 屏，23 ms**：`setReveal()` 把清漆从 0 渐变上来，MeshPhysicalMaterial 的清漆跨过 0 会换一套着色器（`clearcoat` setter 递增 version），于是又编译一次。现在清漆最低 1e-3，淡入全程同一套着色器。
3. **下一章唤醒约 1.25 屏，21 ms**：结构拆解的视图在拖出字标的过程中被唤醒（新建 WebGL 上下文、环境贴图预滤波、编译、上传贴图）。现在 `manageContexts()` 除首屏外的唤醒经过 `wakeGate`：行驶期间（`HERO_CUE.hold` 到拖出结束 1.8 屏）先排队，行驶结束或滚动停下 0.35 s 后再唤醒。结构拆解在桌面 3.25 屏、手机 3.38 屏处进入视口，仍有约半屏余量；实测滚到时已编译完成。

修后同样的扫描（桌面 1440 × 900）：首屏每帧渲染都在 8 ms 内，唯一的长帧移到 1.91 屏（行驶结束后、唤醒结构拆解时）。手机上这几次编译原本各要数百毫秒，这是卡顿的主要来源；未在真机上复测，iOS Safari 的 `compileAsync` 可能不是并行编译。`viewer.js` v35、`logo-tow.js` v4、`explore.js` v83。
